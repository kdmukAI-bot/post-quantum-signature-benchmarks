1Broad findings

This page times post-quantum signature schemes on five boards and compares them with the hardware wallets in Blockstream's tests:

  • Pi Zero and Pi Zero 2 W: SeedSigner runs on them today.
  • ESP32-P4: the initial target for SeedSigner's port to MicroPython, now in progress.
  • ESP32-S3 and RP2350: smaller chips for a possible stripped-down, ultra-low-cost SeedSigner.

Averaged over SLH-DSA-SHA2-128s and SPHINCS+ 2^40 signing [3]; the Trezor Safe 7 row covers one scheme. The Pi Zero 2 W ran at 1 GHz [4]. The wallet figures are Blockstream's, timed differently from ours; Table 11 has the per-scheme times.

SeedSigner's current and future hardware signs in seconds

Signing with SLH-DSA-SHA2-128s, the standardized hash-based scheme that needs nothing saved between signatures:

  • SeedSigner ecosystem boards: under 10 seconds.
  • Hardware wallets in Blockstream's tests: 53 to 120 seconds.

Can the wallets go faster?

  • Same chip, different result: the Jade Plus uses the same chip as our ESP32-S3 board, yet our build signs about 7 times as fast, largely by making better use of the chip's SHA-256 hardware.
  • Trezor too: a Trezor developer's test firmware signed about 3 times as fast as Blockstream's Trezor figure, using a hash unit that production Trezor firmware does not let applications use [2].
  • Open question: how much faster the other wallets could sign.

The full results, with run counts and every measured figure, follow in section 3.

5Not measured

  • ML-DSA with OpenSSL's Keccak assembly on the Pi Zero 2 W and Pi Zero: it would add integration code of our own between mldsa-native and OpenSSL (mldsa-native's custom FIPS 202 header hook), and c-fn-dsa has no such hook.
  • FN-DSA with native double precision on the Pi Zero 2 W and Pi Zero: c-fn-dsa uses native floating point only on x86 with SSE2, 64-bit ARM with NEON, and 64-bit RISC-V with the D extension, so it has no native path on the Pi Zero 2 W in 32-bit mode or on the ARMv6 Pi Zero, and a native-precision figure would need a second implementation.
  • The Pi Zero 2 W in 64-bit mode, or on more than two cores: SeedSigner OS runs it in 32-bit mode, and Blockstream's dual-core code assumes one helper task.
  • Lattice code in IRAM on the ESP32 boards or in SRAM on the RP2350: at level 3 the lattice code stays in flash, because IRAM placement would compete for internal RAM with the ML-DSA-87 task stack and the hash-based code already placed there; on the RP2350, a build with all code in SRAM leaves too little heap for the ML-DSA-87 job's stack.
  • ML-DSA in assembly on the RP2350: mldsa-native v2.0.0's Arm code is for AArch64 NEON and Armv8.1-M MVE, neither of which the Cortex-M33 has.
  • Hedged signing: ML-DSA and FN-DSA were timed with deterministic signing only; hedged signing adds one 32-byte random draw per signature outside the rejection loop.
  • Lattice schemes at level 2: neither the ESP32 SHA units nor the RP2350's SHA-256 accelerator computes SHAKE, and no OpenSSL-backed SHAKE path was built for the Pi Zero 2 W or Pi Zero, so a level-2 build would run the level-1 lattice code.
  • NIST's additional-signature candidates (for example SQIsign, HAWK, and MAYO): not standardized, and their parameters still change between rounds.
